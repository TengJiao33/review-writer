# Skills 工作流说明

Review Writer 的主流程不是八个只能向前走的阶段，而是三个可以往返的质量闭环：

```text
证据闭环  <->  文章与图表闭环  <->  发布闭环
检索/全文/证据    论点/正文/表图       审校/导出/逐页检查
```

每次开始工作或完成实质修改后，先运行：

```bash
python skills/review-writing-orchestrator/scripts/review_cycle.py \
  --review-root . --project-id <project_id> --write
```

`review_state.json` 会指出当前最值得处理的质量欠债。已有文件不代表闭环完成；证据不足时必须重新检索和深读，表图或反例改变论述时必须回到文章结构，发布问题必须回到源产物修改。

## 权威产物

- `00_discovery/topic_contract.json`：本次交付承诺的主题和范围，运行中不能伪造用户批准来缩小。
- `01_matrix_outline/literature_matrix.json`：带原文位置的证据账本；标题、摘要和元数据不能冒充全文证据。
- `01_matrix_outline/section_blueprint.json`：基于证据写成的论点地图。初始化脚本只生成待改写的编辑提示，不能直接拿去写正文。
- `02_section_drafting/section_drafts.json` 与图表 manifest：正文、表格和图片是同一个文章计划，必须保留读者用途、证据、核验和插入位置之间的连接。
- `05_final_audit/final_draft.md`、`final_draft.docx`、`final_draft.pdf`：经过独立挑战、结构检查和逐页视觉检查的交付物。

Markdown、CSV、状态报告和验证报告都是由上述产物生成的视图，不应手工修改来改变结果。

## 执行原则

- QoderWork 直接编辑项目的规范 JSON/Markdown 产物；不要为单次实验创建生成、修复、审校或补录日志脚本。
- 仓库脚本负责确定性的提取、验证、合并、插图、引用编号、DOCX/PDF 转换和报告生成，不替模型做科学判断。
- 表格和图片按读者任务选择。来源论文中的图可以在许可和图级署名核验后原样复用；改编必须允许衍生，原创综述图必须绑定证据并独立核验。
- 语义审校要重新打开来源并留下可校验的原文回执。同一个写作者不能用“已检查”布尔值替代反证式审读。
- 只有证据、文章/图表和发布三类质量欠债都解决后，才运行严格完成检查和实验 finalizer。

原来的各个 Skill 仍作为执行工具使用：

```text
review-topic-paper-discovery
review-literature-matrix-outline
review-section-blueprint
review-section-drafting-figure-picking
review-figure-style-redraw
review-draft-merge-polish
review-final-audit-release
review-export-docx
```

它们不是必须一次通过的门，也不规定成品只能按固定顺序生长。
